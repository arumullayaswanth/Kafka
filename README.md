# Kafka E-commerce Demo

Place an order in a React shop, publish it to Kafka, consume it, watch it update live, and inspect the same event in Kafka UI. Runs on one EC2 instance with Docker Compose.

```
kafka-ecommerce-demo/
├── docker-compose.yml   .env.example   .gitignore   README.md
├── frontend/   React (Vite) → nginx. components/, pages/, services/api.js
├── backend/    FastAPI. routes/, services/, models/, kafka/producer.py, config.py
├── consumer/   Python consumer, group order-processing-group
├── kafka/      init-topic.sh, config/server.properties (reference)
├── scripts/    start.sh stop.sh logs.sh health-check.sh test-kafka.sh
└── docs/       architecture.md deployment.md troubleshooting.md
```

## Quick start

```bash
./scripts/start.sh            # creates .env with a random token, builds, starts
./scripts/health-check.sh
./scripts/test-kafka.sh       # automated end-to-end test
```

- Shop: `http://EC2-PUBLIC-IP` (pages: Shop, Orders, Live Event Monitor)
- Kafka UI: `http://EC2-PUBLIC-IP:8080`

Only ports 80 and 8080 are published, and both should be limited to your IP in the security group. Kafka (9092) and the backend (8000) stay on the Docker network.

## What each part does

| Part | Details |
|---|---|
| Kafka | `apache/kafka:3.8.0`, KRaft single node, volume `kafka-data`, healthcheck, advertised listener `kafka:9092`. Topic `orders` is created by `kafka-init` (3 partitions, RF 1). |
| Backend | `POST /api/orders` (validate, price server-side, publish with key = `order_id`, return ID + status + partition + offset), `GET /api/orders`, `GET /api/products`, `GET /health`, `/ws` WebSocket (orders, events and partition assignments). Kafka is polled every 3 s for group membership. |
| Consumer | Group `order-processing-group`, manual commit after processing, logs partition assignments, reports `PROCESSED` to the backend. |
| Frontend | Product cards with quantity, Place Order, confirmation with publish status, live order history and a live event monitor (order ID, product, amount, event status, timestamp, partition, offset) over WebSocket. |
| Kafka UI | Brokers, topics, partitions, messages (key and JSON value), consumer groups, offsets, lag. |

## Multiple customers and consumer groups

```
Customer 1..5 ─► Frontend ─► FastAPI (producer) ─► topic orders [P0 P1 P2]
                                                         │
                 ┌───────────────────────────────────────┼───────────────────────────────────┐
     order-processing-group               payment-processing-group                notification-group
     order-consumer-1/2/3                 payment-consumer-1/2/3                  notification-consumer-1/2/3
     status → PROCESSED                   payment → PAYMENT_CONFIRMED             notification → NOTIFICATION_SENT
```

- All three groups subscribe to `orders`, so **each group receives every order**.
- Inside a group, the 3 partitions are split so **each consumer owns one partition**. That makes 9 consumer containers in total. They all use one image (`consumer/`), and `CONSUMER_ROLE` chooses the group.
- On the Shop, type your name, choose products and quantities, then click **Place Order**. `./scripts/test-kafka.sh` places five orders (Customer 1 to 5) through the API.
- *Orders* shows three status columns per order, one per group, with the consumer that handled it. *Live Event Monitor* shows the partition → consumer table for each group, updated live on rebalance.
- To see a rebalance, run `docker compose stop order-consumer-3`. Its partition moves to another member within about 10 s. Then run `docker compose start order-consumer-3` to restore it.
- In Kafka UI → Consumers you'll find three groups, each with 3 members, plus committed offsets and lag per partition.

## Manual end-to-end walkthrough

1. Open the Shop, pick products, click **Place Order**. The confirmation shows the order ID, `PUBLISHED`, partition and offset.
2. The row in *Recent Orders* turns `PROCESSED` once the consumer finishes. The *Live Event Monitor* shows `ORDER_PUBLISHED` then `ORDER_PROCESSED`.
3. In Kafka UI: Topics → orders → Messages, search the order ID. Key, partition and offset match. Consumers → order-processing-group shows members, committed offsets and lag.
4. Rebalance: `docker compose stop order-consumer-3`, and within about 10 s another member takes its partition (Live Event Monitor and Kafka UI). Run `docker compose start order-consumer-3` to restore it.
5. Persistence: `docker compose restart kafka`. Offsets and messages survive. `./scripts/stop.sh --purge` deletes them.

## Configuration (`.env`)

`INTERNAL_API_TOKEN` (required, secret, generated by `start.sh`), `FRONTEND_PORT`, `KAFKA_UI_PORT`, `TOPIC_NAME`, `KAFKA_CLUSTER_NAME`. `.env` is git-ignored. Commit only `.env.example`.

## Kafka concepts

- **Broker**: a Kafka server that stores partitions. This demo has one, which also acts as KRaft controller (no ZooKeeper).
- **Topic**: a named stream of records (`orders`).
- **Partition**: an ordered log inside a topic. Records with the same key land in the same partition, so order is preserved per key.
- **Producer**: writes records. The backend publishes each order with its ID as key.
- **Consumer / consumer group**: consumers sharing a `group.id` split a topic's partitions, one owner per partition. With 3 partitions, a 4th consumer sits idle.
- **Offset**: a record's position within a partition. The committed offset is where a group resumes. Lag is log-end offset minus committed offset.
